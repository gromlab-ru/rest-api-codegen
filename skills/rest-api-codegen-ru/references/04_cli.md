# CLI

CLI используется только для автоматического сценария: он читает OpenAPI JSON и создаёт самодостаточный клиент. Для ручного API пакет устанавливается как обычная зависимость, а CLI не запускается.

## Запуск через `npx`

Устанавливать генератор в проект не требуется. Основная форма запуска:

```bash
npx --yes @gromlab/rest-api-codegen@5.2.0 \
  --input <openapi.json-or-url> \
  --output <directory>
```

Короткие параметры:

```bash
npx --yes @gromlab/rest-api-codegen@5.2.0 \
  -i ./openapi/openapi.json \
  -o ./src/generated
```

Всегда указывайте точную версию генератора, если храните результат в Git или запускаете генерацию в CI. Версия `latest` может изменить сгенерированные файлы даже без изменений OpenAPI.

Если пакет уже установлен для ручного сценария, команда `rest-api-codegen` также будет доступна локально. Устанавливать пакет только ради генерации не нужно.

## Параметры

| Параметр | Обязательный | Назначение |
| --- | --- | --- |
| `-i, --input <path>` | да | Локальный JSON-файл либо URL с `http://` или `https://`. |
| `-o, --output <path>` | да | Каталог для сгенерированного клиента. |
| `-V, --version` | нет | Версия CLI. |
| `-h, --help` | нет | Справка. |

Других режимов нет. Параметры `--mode`, `--name`, `--single-file` и `--swr` не поддерживаются. Ручное создание API - не режим CLI; для него используются публичные экспорты пакета.

## Команда npm

Для регулярного запуска сохраните полную `npx`-команду:

```json
{
  "scripts": {
    "generate:pet-store-api": "npx --yes @gromlab/rest-api-codegen@5.2.0 --input ./openapi/pet-store.openapi.json --output ./src/infra/pet-store-api/generated"
  }
}
```

```bash
npm run generate:pet-store-api
```

При обновлении генератора версия меняется явно в одной команде, а изменения сгенерированных файлов проверяются вместе с ней.

## Входная спецификация

CLI всегда разбирает входные данные через `JSON.parse`. YAML не поддерживается.

Если исходная specification хранится в YAML, сначала ищите уже настроенный и зафиксированный по версии OpenAPI bundler проекта. При наличии external `$ref` создавайте самодостаточный bundled JSON: простое преобразование синтаксиса YAML в JSON не разрешает внешние ссылки. Если toolchain ещё не выбран, согласуйте и зафиксируйте bundler либо запросите готовый bundled JSON, не полагаясь на случайную transitive dependency.

Перед передачей преобразованного файла CLI проверьте, что он разбирается как JSON, содержит ожидаемые `openapi`/`swagger`, `info` и `paths`, а generated SDK проходит typecheck.

Перед генерацией проверяется минимальный структурный контракт:

- корень является JSON-объектом;
- присутствует строковое поле `openapi` или `swagger`;
- `info` является объектом;
- `paths` является объектом.

Это не заменяет полноценную семантическую проверку OpenAPI. Неверно описанный метод может дать типизированный код, который не соответствует реальному API. Для временного исправления используйте [смешанный сценарий](./07_custom-operations.md).

## Локальный файл

```bash
npx --yes @gromlab/rest-api-codegen@5.2.0 \
  --input ./openapi/openapi.json \
  --output ./src/generated
```

Если файл не существует, CLI завершится с кодом `1` до генерации.

## URL

```bash
npx --yes @gromlab/rest-api-codegen@5.2.0 \
  --input https://api.example.com/openapi.json \
  --output ./src/generated
```

Документ загружается один раз. CLI не позволяет настроить заголовки, авторизацию, тайм-аут или повторные попытки для загрузки закрытой спецификации.

Для закрытого URL сначала определите auth scheme и источник credentials. Скачивайте specification отдельным контролируемым шагом с ошибкой на non-2xx status и timeout; secret берите из environment или secret store и не записывайте в repository, script либо logs. После загрузки проверьте JSON и минимальную OpenAPI structure. Решение о commit локального файла принимайте по политике проекта: закрытый contract можно хранить как временный ignored artifact, но generation script должен уметь воспроизводимо получить его заново.

## Безопасная замена каталога

Новый клиент сначала полностью создаётся в соседнем временном каталоге. После успешной генерации прежний каталог становится резервной копией, а временный занимает его место. Если замена завершается ошибкой, генератор пытается восстановить резервную копию.

Следствия:

- старые сгенерированные файлы удаляются;
- любые ручные файлы внутри каталога результата удаляются;
- при ошибке чтения, разбора или генерации предыдущий результат сохраняется;
- для результата нужен отдельный каталог, например `src/generated`.

## Код завершения и сообщения

- `0` - клиент успешно создан.
- `1` - ошибка аргументов, входного файла, сети, JSON, OpenAPI или записи результата.

Не определяйте успех по наличию старого результата. Всегда проверяйте код завершения процесса.

## Воспроизводимая генерация

Зафиксируйте версию генератора непосредственно в `npx`-команде и основную версию Node.js в CI. Если сгенерированный клиент хранится в Git, проверяйте изменённые, удалённые и новые файлы. Подробный сценарий приведён в рецепте [воспроизводимой генерации](./recipes/package/generation-ci.md).
